## Mission

Review whether Terminal Zero has the right quant research and backtest validity gates to become a real strategy + data research engine. The goal is not to approve any strategy for trading. The goal is to define what evidence is required before a strategy, signal, candidate, replay, or dashboard surface can be called research-valid.

## Review Sequence

1. Confirm the canonical simulation/backtest path.
2. Confirm point-in-time data boundaries.
3. Confirm benchmark, costs, universe, and window policy.
4. Confirm evidence thresholds for strategy promotion.
5. Identify which current outputs are only diagnostics or status objects.
6. Propose the smallest next implementation slice that improves research validity.

## High-Value Real Questions

1. What is the canonical backtest path?
   - Should every strategy go through `core.engine.run_simulation`, `strategies.strategy_replay`, a strategy adapter, or another single path?
   - Which existing scripts are legacy experiments and should not define research validity?

2. What is the minimum strategy cartridge contract?
   - Required fields: universe, PIT input loader, rebalance schedule, costs, slippage, benchmark, signal definition, position sizing, risk constraints, cash handling, output metrics.
   - What should fail closed if missing?

3. What is the minimum evidence packet before a strategy can move from "research object" to "candidate strategy"?
   - Required metrics: CAGR, volatility, Sharpe, Sortino, max drawdown, turnover, hit rate, exposure, beta, alpha, benchmark-relative return, cost drag, drawdown duration.
   - Which metrics are mandatory versus advisory?

4. What baseline is valid?
   - Should the baseline be SPY, QQQ, Russell 3000, cash, equal-weight universe, current C3 baseline, or strategy-family-specific?
   - How should the repo prevent cherry-picking baselines?

5. What window policy is acceptable?
   - Minimum in-sample/out-of-sample span?
   - Walk-forward requirement?
   - Regime coverage requirement?
   - How should short local data windows be labeled?

6. What costs and frictions must be non-optional?
   - Commission, spread, slippage, borrow/short costs, turnover penalty, market-impact proxy, tax/cash drag?
   - Which are required for long-only research now?

7. How should PIT discipline be proven?
   - Date slicing, universe membership, fundamentals release dates, ticker mapping, corporate actions, stale endpoint handling.
   - What proof should be in tests versus generated evidence artifacts?

8. What constitutes leakage in the current codebase?
   - Future universe membership?
   - Full-history factor normalization?
   - Endpoint freshness overlays?
   - Candidate-card or dashboard labels feeding strategy logic?
   - Saved replay artifact reuse across mismatched signatures?

9. What is the correct role of Rule100?
   - Is it a strategy, lifecycle replay, diagnostic policy, allocation method, or candidate benchmark?
   - What evidence is missing before it can be compared to alternatives?

10. What is the correct role of the optimizer?
    - Is optimizer output research evidence, portfolio construction policy, diagnostic allocation, or UI control output?
    - What must be true before optimizer weights can be used in a backtest?

11. What is the correct role of candidate cards and signal cards?
    - Are MU/MSFT cards research inputs, hypotheses, evidence objects, or UI status objects?
    - What evidence transforms them into strategy-testable hypotheses?

12. What should the dashboard be forbidden to imply?
    - Which labels still sound like recommendations, rankings, scores, alerts, or buy/sell/hold decisions?
    - What exact wording would make the UI research-safe?

13. What tests are missing for research validity?
    - Which tests should be added before new strategy work?
    - Which current tests prove mechanics but not research validity?

14. What data-health failures should invalidate a backtest?
    - Stale endpoints, missing returns, non-finite returns, partial price history, wrong price/return slots, missing PIT membership, unresolved permnos.
    - Which should produce cash-closed output versus full failure?

15. What artifacts should be generated by every valid backtest?
    - Metrics JSON, equity curve, trades, daily positions, exposure, turnover, benchmark curve, cost breakdown, input signatures, source file signatures, PIT proof.

16. What should be archived or quarantined?
    - Which backtest scripts/results are useful historical context but should not be treated as current validity evidence?

17. What is the one-week quant validity plan?
    - Propose 3-5 bounded milestones.
    - Each milestone needs exact acceptance checks and a clear "what becomes more research-valid" statement.

## Desired Expert Output

- One recommended canonical backtest/evidence architecture.
- One strategy cartridge contract.
- One metric/evidence packet schema.
- One baseline/window/cost policy.
- One PIT/leakage audit checklist.
- One list of current outputs that are status-only, diagnostic-only, research-valid, or blocked.
- One first implementation slice with files to touch and tests to run.

## Boundary

Do not approve live trading, broker automation, alerts, rankings, recommendations, autonomous allocation, or public performance claims. This is a research-validity review only.
